Эволюция политик CSP
1. Иллюзия безопасности (Уязвимая)
HTTP
Content-Security-Policy: default-src * 'unsafe-inline' 'unsafe-eval';
Эта политика разрешает загрузку ресурсов откуда угодно, выполнение любых inline-скриптов (<script>...</script>) и использование функций вроде eval().

Вектор атаки: Если в приложении есть отраженная или хранимая XSS, атакующий может просто вставить <script>alert('XSS')</script>, и браузер его выполнит.

Смысл: Отсутствует. Эквивалентно отсутствию CSP.

2. Уязвимый Allow-list (Слабая)
HTTP
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.jsdelivr.net 'unsafe-inline';
Разработчики часто используют белые списки доменов и оставляют 'unsafe-inline' для удобства работы старого кода или аналитики.

Вектор атаки: 'unsafe-inline' сводит на нет защиту от инъекций тегов <script>. Даже если убрать 'unsafe-inline', атакующий может обойти политику, найдя уязвимость типа Open Redirect или JSONP-эндпоинт на разрешенном CDN (например, jsdelivr), чтобы подгрузить свой вредоносный пейлоад.

3. Защита на базе Nonce (Умеренная/Хорошая)
HTTP
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-rAnd0mBase64+String=';
Здесь убирается 'unsafe-inline' и вводится криптографически стойкий одноразовый токен (nonce), который генерируется заново на каждый HTTP-запрос. Скрипт выполнится только если его тег содержит правильный атрибут: <script nonce="rAnd0mBase64+String=">.

Защита: Атакующий не знает nonce заранее, поэтому внедренный им код  <script>... будет заблокирован браузером.

Слабое место: Если разработчик динамически создает скрипты через JS (например, document.createElement('script')), они будут заблокированы, если не прокинуть в них nonce вручную, что усложняет разработку.

4. Strict CSP (Максимально безопасная)
HTTP
Content-Security-Policy: object-src 'none'; base-uri 'none'; script-src 'nonce-{random}' 'strict-dynamic' 'unsafe-inline' https: http:;
Это современный стандарт "Strict CSP", рекомендованный Google. Он решает проблему белых списков и упрощает работу со сложными фронтенд-фреймворками.

'nonce-{random}': Базовая защита скриптов.

'strict-dynamic': Говорит браузеру: "Если скрипт был загружен с правильным nonce, доверяй всем новым скриптам, которые этот скрипт попытается загрузить динамически".

'unsafe-inline' https: http:: Эти директивы игнорируются современными браузерами, если присутствует nonce или hash. Они нужны исключительно для обратной совместимости со старыми браузерами (например, Safari 9), которые не знают про 'strict-dynamic'.

object-src 'none' и base-uri 'none': Блокируют инъекции Flash/Java апплетов и подмену базового URL для относительных ссылок (защита от атак через тег <base>).
